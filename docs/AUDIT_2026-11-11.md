## Arxitektura

```text
sources → scraper → filters → source dedup → resolver
       → URL/title/semantic dedup → Gemini editor
       → post_builder → Telegram → Supabase persistence
Supabase posted deadlines → reminders → Telegram
GitHub Actions → tests → scheduled run → log artifact + admin summary
```

Afzalliklari: modullar vazifasi ajratilgan; post muharriri URL o'rniga index
ishlatadi; HTML escape va rich/HTML ko'rinishlari bitta mazmundan quriladi;
manbalar parallel yig'iladi; domen bo'yicha throttle va workflow concurrency bor.
Mavjud arxitekturani qayta yozish talab qilinmaydi.

## Qolgan muhim ishlar

1. **Durable outbox va reconciliation (P1).** Telegram yuborishi va Supabase yozishi
   bitta tranzaksiya emas. Telegram postni qabul qilib, HTTP javobi yo'qolsa yoki
   DB keyin yiqilsa, qayta yurishda takror bo'lishi mumkin. Rich/HTML yarim
   yuborilishi uchun ham xabar/grant kesimida journal kerak. Yechim: yuborishdan
   oldin intent yozish, message ID'larini saqlash, noaniq natijani `uncertain`
   qilib operatorga chiqarish; butun to'plamni ko'r-ko'rona qayta yubormaslik.
   Hozirgi tuzatish xatoni oshkora qiladi, bu oynani butunlay yopmaydi.

2. **Baza ruxsatlari (P1).** RLS dashboard'da o'chirilgan. Anon/authenticated
   rollarining real GRANT'lari va ishlayotgan bot kalitining roli aniqlanib,
   backend uchun kerakli huquqlar tasdiqlangandan keyin RLS siyosati qo'llansin.
   Ochiq kirish mavjudligi faqat RLS disabled belgisidan isbotlanmaydi; kalit
   turini tekshirmasdan RLS yoqish botni to'xtatishi mumkin.

3. **Barqaror retry navbati (P2).** Yangi havola xatolari endi yo'qolmaydi, lekin
   har yurishda yana ko'riladi. DB'da attempts/next_retry_at/reason bilan cheklangan
   backoff va uzoq muddatli backlog kerak. Eski 2 638 skipped yozuv xato yoki
   haqiqiy rad etishligini sxema saqlamagan; ularni ommaviy qayta post qilish mumkin emas.

4. **Grant sikli identifikatori (P2).** Bir URL yoki invariant dastur slug'i keyingi
   yilgi qabulni ham takror deb yashirishi mumkin. Program va application_cycle'ni
   ajratish, eski yozuvlarni ehtiyotkor backfill qilish talab etiladi.

5. **Sifat va samaradorlik o'lchovi (P2).** Low/high uchun bir xil 30–50 nomzodni
   kanalga yubormasdan taqqoslash: O'zbekiston fuqarosiga moslik, deadline aniqligi,
   rasmiy URL aniqligi, p50/p95 vaqt, har qabul qilingan grantga token sarfi.
   Keyin thinking/batch/workers uchun haqiqiy optimal qiymat tanlanadi.

6. **Manba holati va scheduler (P2).** Shu yurishda `mladiinfo` faqat eski yozuvlar,
   `tg:mininnovation` 15 ta eski post, `tg:eyuf` nol post bergan. Nol natija bitta
   o'lchov bilan manba butunlay ishlamaydi degani emas. Har manbaning last_success,
   fresh_count, accepted_count va xato sababini saqlash kerak. Cron 05:20 Toshkentga
   qo'yilgan, lekin shu kuni 11:38 da boshlangan; qat'iy nashr vaqti kerak bo'lsa,
   Actions tashqarisida scheduler/queue tanlash kerak.

## Joriy o'zgarishlarni chiqarish tartibi

1. Lokal diffni shu audit bilan ko'rib chiqish va remote branch/PR'ga chiqarish.
2. Yangi offline checks Linux/Python matritsasidan o'tishi.
3. Ishlayotgan secrets bilan `dry_run=true`, `test_message=false` yurishi.
4. Natijadagi kartochkalarni sifat bo'yicha tekshirish, keyin odatiy kunlik yurish.
5. Birinchi jonli yurishdan keyin post va DB hisoblarini solishtirish; eski skipped
   qatorlarni avtomatik tozalamaslik/qayta ochmaslik.

Bu tuzatishlar mavjud jadval uchun yangi migratsiya talab qilmaydi.
Faol CLI akkaunti repo uchun `push: false`; remote'ga yozish yoki production
o'zgartirish bajarilmadi. Brauzer orqali Supabase faqat o'qildi.
